# ADR 0008: 업데이트 파일은 별도 공개 저장소에 둔다

- 상태: 승인 — 2026-10-17, 0.15.5부터 적용
- 관련: [ADR 0007](0007-partial-updates.md), 릴리스 절차의 Release 게시와 철회

## 배경

ADR 0007로 Release마다 구성별 업데이트 설치기, 변경분 ZIP, 업데이트 색인이 붙는다. 변경분 ZIP은 직전 최대 3개 버전 × 2개 구성이라 본 저장소 `leewb2280/watched-kettle`의 Release 첨부가 12개 안팎까지 늘어난다.
사람은 그중 통합 설치기와 `.sha256`만 받는다. 앱은 같은 Release 안의 첨부만 고르므로 업데이트 파일을 다른 곳에 두려면 앱이 읽는 주소부터 바꿔야 한다.

0.15.3과 0.15.4 설치판은 본 저장소의 `releases/latest`를 읽는다. 0.15.3은 통합 설치기와 `.sha256`만 찾는다. 0.15.4는 색인이 있으면 변경분을, 없으면 통합 설치기를 고른다.

## 결정

### 저장소

| 저장소 | 공개 | 내용 | Release 첨부 |
|---|---|---|---|
| `leewb2280/watched-kettle` (본 저장소) | 공개 | 공개 소스 | 통합 설치기 `WatchedKettle-<v>-public-unsigned-setup.exe`와 `.sha256` |
| `leewb2280/watched-kettle-updates` (업데이트 저장소) | 공개 | 안내 README 하나 | 통합 설치기와 `.sha256`(본 저장소와 같은 바이트), 구성별 업데이트 설치기 2개, 변경분 ZIP, `update.json`과 `.sha256` |

- 업데이트 저장소는 인증 없이 API와 첨부를 읽어야 하므로 공개한다. 소스는 두지 않고 Issues·Wiki·Projects를 끈다. README는 앱 안 업데이트 전용이라는 것과 본 저장소 Releases를 안내한다.
- 두 저장소 모두 `v<버전>` 태그를 쓴다. 업데이트 저장소의 태그는 README 커밋에 붙이는 경량 태그이고 소스와 관계없다.
- 업데이트 저장소에도 통합 설치기를 올린다. 색인이 없거나 읽지 못할 때, 그리고 변경분과 구성별 설치기를 쓸 수 없을 때의 마지막 대체 경로다. 앱은 다른 Release의 첨부를 받지 않는다.
- 업데이트 저장소의 Release 본문은 한 줄이다. "Watched Kettle v<버전> 앱 안 업데이트용 파일. 변경 사항: <본 저장소 Release 주소>".

### 앱이 읽는 주소

`watched_kettle/branding.py`에 두 값을 둔다. `scripts/build_windows.ps1`이 Public 빌드의 `UPDATE_SOURCE.json`에 쓴다.

| 키 | 값 | 쓰임 |
|---|---|---|
| `api_url` | `https://api.github.com/repos/<UPDATE_REPOSITORY>/releases/latest` | 업데이트 확인 |
| `release_url` | `https://github.com/<UPDATE_REPOSITORY>/releases` | 응답의 `html_url`이 이 주소 아래인지 확인 |
| `notes_url` (선택) | `https://github.com/<RELEASE_REPOSITORY>/releases` | `변경 사항 보기`가 `<notes_url>/tag/v<버전>`을 연다 |

- `notes_url`은 `release_url`과 같은 규칙으로 검사한다. 공식 채널이면 `https://github.com`, 시험 채널이면 API와 같은 주소·포트다. 맞지 않으면 업데이트 주소 설정 오류로 보고 확인하지 않는다.
- `notes_url`이 없으면(이 결정 이전 형식, 시험 채널의 주소 파일) 지금처럼 응답의 `html_url`을 연다.
- 허용 호스트(`api.github.com`, `github.com`, GitHub 첨부 서버)는 바꾸지 않는다. 저장소 경로는 이전처럼 제한하지 않는다.
- `UPDATE_SOURCE.json`은 번들 manifest에 들어간다. 그래서 0.15.4→0.15.5 변경분 ZIP에 새 주소 파일이 함께 들어가고, 0.15.5부터는 업데이트 저장소를 읽는다.

### 0.15.5 전환

0.15.5의 본 저장소 Release에만 0.15.4용 업데이트 파일을 함께 올린다. 첨부는 6개다.

- 통합 설치기와 `.sha256`
- `WatchedKettle-0.15.5-update.json`과 `.sha256`(업데이트 저장소와 같은 파일)
- `-from-0.15.4.zip` 2개(구성별)

구성별 업데이트 설치기는 올리지 않는다. 0.15.4 앱은 색인에 적힌 구성별 설치기가 Release에 없으면 통합 설치기로 대체한다. 그래서 변경분을 적용하지 못해도 업데이트는 된다.
0.15.6부터 본 저장소 Release는 2개다. 0.15.3·0.15.4 설치판을 위해 통합 설치기 이름 규칙(`WatchedKettle-<v>-public(-unsigned)-setup.exe`와 `.sha256`)은 계속 지킨다.
0.15.5에서 설치기 개정 번호가 오르면 0.15.4에서 오는 변경분이 생기지 않는다. 그때는 본 저장소에 2개만 올린다.

### 게시 순서

두 Release를 draft로 만들어 첨부·본문을 확인한 뒤 게시한다.

- 기본: 본 저장소를 먼저, 업데이트 저장소를 바로 다음에 게시한다. 앱이 새 버전을 볼 때 `변경 사항 보기` 대상과 사람이 받을 파일이 이미 있다.
- 0.15.5만 예외로 업데이트 저장소를 먼저 게시한다. 그 저장소를 읽는 설치판이 아직 없으므로 사용자에게 보이지 않고, 실제 `releases/latest` 응답을 본 저장소 게시 전에 확인할 수 있다.

| 한쪽만 게시된 상태 | 영향 |
|---|---|
| 본 저장소만 | 0.15.3·0.15.4는 정상. 0.15.5 이후 설치판은 아직 이전 버전을 최신으로 본다(0.15.5 첫 게시라면 "아직 공개된 배포가 없습니다") |
| 업데이트 저장소만 | 0.15.5 이후 설치판이 업데이트를 받지만 `변경 사항 보기`가 404다. 오래 두지 않는다 |

철회는 두 저장소를 함께 한다. 본 Release를 prerelease로 바꾸거나 지우면 같은 버전의 업데이트 Release도 같이 처리한다.

## 확인 방법

1. 게시 전 선택 확인: 본 저장소용 첨부 6개를 한 폴더에 모아 `scripts.serve_update_test --release-dir`로 낸다. 공개 태그 v0.15.4 소스를 설치판처럼 꾸민 임시 폴더에서 실행해 두 구성이 `from-0.15.4` ZIP을 고르는지 본다. `--mode bad-delta`에서는 통합 설치기로 바뀌는지 본다. 업데이트 저장소용 폴더와 0.15.5 소스로도 같은 확인을 한다.
2. draft 대조: 두 draft Release의 첨부 이름·크기(`gh release view --json assets`)를 로컬 SHA-256·색인과 맞추고, 두 Release의 통합 설치기·색인이 같은 바이트인지 확인한다.
3. 게시 뒤 자동 조회: 실제 GitHub API로 0.15.4 소스는 본 저장소의 변경분을, 0.15.5 소스는 업데이트 저장소의 Release를 고르는지 확인한다.
4. 실제 설치판의 0.15.4→0.15.5 변경분 적용과 그 뒤 업데이트 저장소 조회는 실환경 검수로 따로 남긴다. 1~3은 실환경 검수가 아니다.

## 한계

- 본 저장소와 업데이트 저장소에 같은 통합 설치기를 두 번 올린다. 두 첨부가 다르면 사람이 받은 파일과 앱이 받은 파일이 달라지므로 게시 전에 SHA-256을 대조한다.
- 업데이트 저장소에 Release를 올릴 권한을 빼앗기면 그 저장소를 읽는 설치판이 영향을 받는다. 신뢰 범위는 ADR 0007과 같고, 코드 서명을 정하면 서명 확인을 더한다.
- 0.15.4 설치판이 0.15.5를 건너뛰고 0.15.6 이후로 올라가면 본 저장소에 색인이 없어 통합 설치기를 받는다.
